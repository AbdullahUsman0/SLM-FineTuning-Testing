# Window-close abort and same-run recovery, 2026-10-19 PDT

The actual trainer stopped at unsaved optimizer step 156. Its log reports `forrtl: error (200): program aborting due to window-CLOSE event`. The worker and trainer disappeared, while their JSON status still said running. The PC had not rebooted. This incident has direct evidence of a console-close abort; temperature is not attributed as its cause. The compressed abort-log excerpt preserves the exact captured bytes; the complete original log remains in the run directory.

Checkpoint 150 was independently verified, including all 11 artifact SHA-256 values and the original run fingerprint. The same supplied `run.py start --run SAME_PATH` was launched at approximately 23:48 PDT. No prepare/new run/zero restart/counter edits, data changes, model changes or hyperparameter substitutions occurred. Fresh optimizer progress after resume is recorded in live-resume-confirmation.json. Steps 151–156 were unsaved before the abort and must be replayed.

The previous hidden launcher still allowed Windows venv redirectors to allocate console windows. The repair uses local WMI process creation through `WmiPrvSE.exe`, requests DETACHED_PROCESS | NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB, and runs a hash-verified command capsule with logs on disk. An opt-in startup helper on an auxiliary PYTHONPATH calls Windows FreeConsole before model imports and hides the associated launcher console. Its only role is Windows process lifetime: it does not modify model computation, training data, optimizer state, generation settings or frozen training source. `SLM_DETACH_WINDOWS_CONSOLE=1` scopes the helper to these launched descendants. No additional dependencies were installed. Both helper versions and their per-process hashes are retained. The existing live trainer loaded v1; its remaining native launcher window was then hidden directly. Future child processes use v2, which hides that window before detaching. These technical environment changes are explicit, not part of a newly selected model experiment.

WMI ancestry and actual Python console detachment were measured. Job membership still reports true in this environment; complete escape from every Windows job container is NOT claimed. A three-level harmless starter/worker/trainer simulation matched the supplied launch flags, survived starter exit, and reported no console in any actual Python process. Ten recovery-policy/isolation tests passed, including a child that remains alive after its initiating shell returns. Initial failed isolation attempts remain preserved in the external control directory; test-findings.json records their findings and corrected assumptions. No live model process was killed to apply the repair. The idle polling companion alone was safely replaced with the unchanged followup-r4 source under the new launcher.

Hourly/sign-in monitoring now uses r3 with the same checkpoint verification, duplicate-process protection and two-attempt-per-24-hour automatic recovery cap. This user-requested repair/recovery is recorded in the shared recovery history. Further recurring failures at the cap require review, rather than an endless restart loop. The task cannot keep training alive through PC shutdown or a policy that terminates the login session. Screen lock is supported. Do not close a Python training launcher or end its task; the log-view command only observes the file.
